# 互动视频游戏创作工具：竞品与开源项目扫描

更新日期：2026-09-10

## 结论先行

这不是空白赛道，但仍没有出现一个已经占据心智的“互动视频游戏领域的剪映”。现有产品通常只覆盖以下三层中的一到两层：

1. 叙事结构：可视化分支、变量、条件与结局；
2. 媒体制作：上传或编辑已经存在的视频；
3. AI 生产：从创作者写好的时间线脚本生成连续、一致的视频，并自动组装可玩逻辑。

你的机会不在于再做一个节点编辑器，而在于把这三层连成一个对小白完整闭环的工作流，并坚持“AI 不替用户写剧情，只补足制作与 coding 能力”。

## 最接近的直接竞品

| 产品 | 已有能力 | 与目标产品的差距 | 最值得借鉴 |
| --- | --- | --- | --- |
| [Stornaway](https://www.stornaway.io/features/) | 成熟的 Story Map、互动按钮、变量化路径、即时试玩、托管与离线交付；无需代码 | 媒体主要是用户已有素材或 Adobe Express 编辑，不是从时间线脚本自动生产一致的视频游戏资产 | Story Island 数据模型、占位视频试玩、发布与多端交付 |
| [Adventr](https://app.adventr.ai/) | 把视频、音频、文字、图层、互动、变量、条件和状态放入统一创作流程，并开始强调 AI Media | 更偏互动媒体/营销与体验平台；是否能稳定产出商业级长叙事视频游戏仍待验证 | 媒体时间线与游戏状态共存的编辑模型 |
| [NEXZONES](https://www.nexzones.com/) | 公开定位几乎完全重合：故事、AI 生成、互动逻辑、测试、版本和发布的一体化无代码系统 | 当前公开内容更像产品主张，成熟度和真实创作者产出尚需实测 | “电影类型 × 游戏形式 × 互动系统”的通用能力模型，以及分支全路径检查 |
| [ManyVerse](https://manyverse.app/features/ai-video-branching-story) | Prompt-first，从世界观和角色描述生成可玩的浏览器分支草稿 | 强调快速原型，并明确不是完整游戏引擎；同时让 AI 生成故事结构，和你的创作者边界不同 | 从想法到可玩草稿的低摩擦体验、浏览器即时分享 |

## 最值得拆解的开源项目

| 项目 | 开源情况 | 可以直接学习的部分 | 注意事项 |
| --- | --- | --- | --- |
| [OpenFMV](https://github.com/Comedian1926/OpenFMV) | MIT；本地优先桌面应用 | 与目标形态最接近：故事蓝图、场景节点、媒体/互动轨道、QTE、试玩和 Web 导出 | 项目尚早期，不能把“已有代码”误判为“需求已被成熟满足”；优先审计其数据模型、播放器和导出协议 |
| [Dream-E](https://github.com/LAION-AI/Dream-E) | MIT | React Flow 节点编辑、角色/地点实体、变量、状态、播放器，以及 AI 图像/TTS/开放世界模式 | 当前视觉表现以图片式视觉小说为主；AI 编剧是核心能力之一，与你的 MVP 边界不同 |
| [Twine](https://play.twinery.org/) | 开源；可直接发布 HTML | 最成熟的小白分支叙事心智；节点图、段落链接和可移植 HTML 输出 | 视频只是嵌入内容，没有视频生产、一致性或专业时间线 |
| [Ren'Py](https://www.renpy.org/) | 开源、可商用 | 经过大量商业作品验证的对话、状态、存档、回滚、跨平台运行时 | 仍然是脚本/代码优先，且官方不提供生成式内容工具；适合作为运行时能力清单，不适合作为小白交互范本 |
| [ink](https://github.com/inkle/ink) | MIT | 高复杂度分支、汇流、变量和条件的叙事表达；适合研究“分支很多但不爆炸”的数据结构 | 文本脚本优先、没有可视化图和媒体生产层 |
| [Go Flow](https://github.com/goflowspace/goflow) | AGPL-3.0 | 无限画布、角色/地点知识库、JSON/HTML/Ren'Py/Unity/Unreal 多格式导出 | AGPL 会影响 SaaS 复用方式，更适合参考而非直接嵌入闭源产品 |

## 市场判断

### 1. 需求已经被多条产品路线验证

“用可视化图管理复杂分支”“不写代码生成可玩的浏览器体验”“在视频上叠加选择与状态”都已有产品验证。用户教育成本不会从零开始。

### 2. 直接竞争比最初想象得更近

NEXZONES 和 OpenFMV 的公开定位已经非常接近你的描述。因此，“我们是第一个互动视频节点编辑器”不能成为定位；它既不准确，也无法形成壁垒。

### 3. 尚未被充分解决的是生产闭环和成品质量

多数工具要求创作者先拥有视频，或者从一句 Prompt 生成粗糙原型。真正困难的是：

- 创作者写完时间线脚本后，不需要理解模型、提示词和首尾帧；
- 多段视频中的角色、场景、表演和镜头衔接能维持商业可用的一致性；
- 选择按钮、变量、条件、跳转和回归点由系统自动实现，但创作者仍能看见并控制；
- 在烧掉大量生成成本前，用占位片段或低成本草稿试玩完整路径；
- 对所有路径做死路、缺失媒体、状态冲突和成本检查。

## 对 MVP 的建议

第一版应把闭环压缩为一个可重复验证的纵向流程：

1. 创作者建立角色和场景资产；
2. 在故事蓝图中连接场景、选择和结局；
3. 为某个场景填写时间线脚本；
4. 系统自动拆镜并生成一致的视频片段；
5. 系统自动把选择、状态和跳转装配到播放器；
6. 创作者无需等全部视频完成，就能试玩所有分支；
7. 系统检查缺失内容、不可达节点、死路与预计生成成本；
8. 一键发布为浏览器可玩的作品。

暂时不要把“AI 自动写故事”纳入 MVP。它会让产品与 ManyVerse、Dream-E 等 Prompt-to-game 工具变得相似，也会削弱你最重要的用户假设：强剧情创作者只需要被补齐制作和 coding 能力。

## 建议的借鉴顺序

1. 先拆 OpenFMV：它是最接近的 MIT 开源实现，重点看项目格式、节点/轨道模型、播放器和导出。
2. 再拆 Stornaway：研究成熟创作者产品如何做占位试玩、Story Map、发布与分支数据。
3. 用 ink/Ren'Py 建立运行时功能清单：变量、条件、分支汇流、存档、回滚、状态检查。
4. 用 Twine 校准小白操作门槛：首次创作不应要求用户理解引擎概念。
5. 持续跟踪 NEXZONES 与 Adventr：它们最可能沿相同方向快速补齐 AI 视频生产层。
