## Confirmed protocol and capability

- Explicit video protocol `tuzi-minimax-h3`, exact base origin `https://api.tu-zi.com`, exact model `MiniMax-H3`. OpenAI Responses/Chat settings are not video protocols.
- Create: `POST /v2/video_generation`, JSON `{model,content,duration,resolution,ratio}`. A nonempty text item is mandatory. `GET /v2/query/video_generation/{system_task_id}` returns `task` status and, on success, `task.content.url` plus optional usage. The gateway's task ID is not the upstream provider ID.
- H3 supports 4–15 whole seconds, 768P/2K, and text-to-video. First-frame image uses a `content` image item with `role=first_frame` and effective `ratio=adaptive`. The [Tuzi video API guide](https://api.tu-zi.com/docs/api/video) states that its gateway accepts data URLs through protected download and staging. The Worker reads only an already verified, project-owned image from private object storage, checks size and SHA-256, and constructs a bounded data URL in memory for the gateway. The adapter rejects arbitrary external image URLs; no private storage key, browser token or public media URL enters the provider request. This path has fake-provider/real-storage tests and one authorized real first-frame product Job.
- The gateway does not document a trustworthy client idempotency contract for this endpoint. A timeout after sending may mean acceptance; a Worker must persist an unknown-submit state and never blindly retry POST. Polling requires a known task ID. The current adapter declares no running-task cancellation; the UI does not promise it. The user's explicit rate authorizes an internal ceiling calculation, distinct from a supplier charge receipt.
- Real 5-second request produced a 5.167-second, 1344×768 H.264/AAC file despite requested 16:9. Treat requested settings as targets and derive accepted metadata from verified bytes.
- On 2026-09-26, one read-only GET of that **same completed system task** through `/v2/query/video_generation/{task_id}` returned HTTP 200 and parsed successfully with the production adapter as `succeeded`. The query reported duration 5 but no usable `total_seconds` (`usageSeconds=null`); neither figure is a provider invoice or a replacement for the saved file's 5.167-second metadata. No new video was submitted or downloaded. See [read-only query evidence](../reports/p2-p3-archive-2026-10-07.md#archived-eb04b1c466b664b3).

### Current integration safety gates

The M2 request service accepts a deployment-managed `VIDEO_PRICE_CONTRACT_JSON` with exact mode/duration/resolution/ratio ceilings in CNY cents, review time and expiry. A missing, malformed, expired or non-matching contract leaves the request unconfirmable. Confirmation additionally requires `VIDEO_PROJECT_BUDGET_CENTS`, `VIDEO_MAX_CONCURRENT_JOBS` and the explicit `VIDEO_CONFIRM_ENABLED=true` gate. The normal local gate is false after the bounded acceptance to prevent further paid calls. Synthetic contracts in tests are not evidence of the user's account tariff.

First-frame mode requires its own exact `mode: "first-frame", ratio: "adaptive"` price entry. H3 ignores a fixed ratio when a first-frame image is provided, so all author-selected ratios in that mode use the same adaptive quote and the UI shows the effective ratio. The stored fixed ratio is only retained for switching a draft back to text-to-video; the actual resulting geometry must be probed from the saved file. Old first-frame contracts with a fixed ratio fail validation and must be reviewed and replaced before confirmation. If the private source image is unavailable before any provider POST, the Worker fails the job and releases the reservation. Once a POST begins, uncertainty remains reserved for reconciliation and is never automatically retried.

Submission has a separate `VIDEO_PROVIDER_SUBMIT_ENABLED` gate, also false by default. A queued job is claimed once with a database lease; a lost or uncertain POST result becomes `submit_unknown` and is never automatically requeued. If the original worker later receives a valid system task ID under the same lease, it may persist that ID. Because the gateway has not documented client idempotency for this endpoint, unknown submissions require the T34 reconciliation path or human review before any new paid attempt.

The gateway system task ID is globally unique across connections in this single-adapter deployment. Manual reconciliation requires an operator's provenance evidence, verifies the ID with a read-only supplier GET using the Job's pinned credential, and refuses an ID already linked to another Job. A verified terminal response is recorded in the same transaction as the audit: success moves to result ingestion; failure or cancellation waits for an actual billing receipt. A running response resumes polling. See [terminal reconciliation evidence](../reports/p2-p3-archive-2026-10-07.md#archived-d9ac506cf217f7fc). This does not prove that a real unknown submission can be identified without supplier-side records.
